# SELECT ... WHERE Call Chain

This note follows this SQL:

```sql
CREATE TABLE users(name TEXT, age INT);
SELECT name FROM users WHERE age = 30;
```

The goal is to see how SQLite moves from SQL text to parser structures, then to VDBE bytecode.

## Big Picture

Parser generation, before SQLite is compiled:

```text
sqlite/src/parse.y
  -> sqlite/tool/lemon.c
       -> Parse()
       -> FindStates()
       -> FindFollowSets()
       -> FindActions()
       -> ReportOutput()
       -> ReportTable()
  -> parse.out
  -> parse.c
  -> parse.h
```

Runtime SQL compilation:

```text
SQL text
  -> sqlite3_prepare_v2() / sqlite3_prepare_v3()
  -> sqlite3Prepare()
  -> sqlite3RunParser()
  -> sqlite3GetToken()
  -> sqlite3Parser()
       -> yy_find_shift_action()
       -> yy_shift()
       -> yy_reduce()
       -> sqlite3PExpr()
       -> sqlite3SelectNew()
  -> sqlite3Select()
       -> sqlite3WhereBegin()
       -> sqlite3ExprCode()
       -> sqlite3VdbeAddOp*()
  -> sqlite3_stmt*
  -> sqlite3_step()
  -> sqlite3VdbeExec()
```

Prepare-time builds the program. Step-time runs the program.

`parse.y` is the human grammar. `parse.c` is the generated parser state machine. `parse.out` is the human-readable report that explains what the generated states mean.

## Tokenizer

`sqlite3RunParser()` lives in:

```text
sqlite/src/tokenize.c
```

It repeatedly calls:

```c
n = sqlite3GetToken((u8*)zSql, &tokenType);
sqlite3Parser(pEngine, tokenType, pParse->sLastToken);
zSql += n;
```

For the query:

```sql
SELECT name FROM users WHERE age = 30;
```

the tokenizer emits roughly:

```text
SELECT  -> TK_SELECT
name    -> TK_ID
FROM    -> TK_FROM
users   -> TK_ID
WHERE   -> TK_WHERE
age     -> TK_ID
=       -> TK_EQ
30      -> TK_INTEGER
;       -> TK_SEMI
```

Whitespace is usually skipped before calling the parser.

## Parser Generation

Lemon is SQLite's parser generator:

```text
sqlite/tool/lemon.c
```

Its template file is:

```text
sqlite/tool/lempar.c
```

The important Lemon functions are:

```text
Parse()          reads parse.y grammar
FindStates()     builds parser states
FindFollowSets() computes lookahead sets for reductions
FindActions()    decides shift/reduce/error actions
ReportOutput()   writes parse.out
ReportTable()    writes parse.c
ReportHeader()   writes parse.h
```

`ReportOutput()` is the function that creates `parse.out`. The useful local files are:

```text
sqlite-debug/parse.out
sqlite-build/parse.out
```

## Generated Parser

`sqlite3Parser()` is generated by Lemon from:

```text
sqlite/src/parse.y
```

The generated C file is:

```text
sqlite-debug/tsrc/parse.c
```

`sqlite3Parser()` itself is mostly a driver. It does not directly contain every semantic action. It calls:

```text
yy_find_shift_action()
yy_shift()
yy_reduce()
```

The important parser idea:

```text
shift  = push a token/symbol onto the parser stack
reduce = matched a grammar rule, run its C action, replace RHS with LHS
```

The current parser state is just a number stored on the top parser stack entry:

```c
yyact = yypParser->yytos->stateno;
yyact = yy_find_shift_action((YYCODETYPE)yymajor, yyact);
```

`yymajor` is the incoming token code, like `TK_ID` or `TK_INTEGER`. `yy_find_shift_action()` looks up:

```text
current state + incoming token -> parser action
```

The returned `yyact` is another number. Lemon uses numeric ranges to encode what it means:

```text
yyact >= YY_MIN_REDUCE      -> reduce by rule number yyact - YY_MIN_REDUCE
yyact <= YY_MAX_SHIFTREDUCE -> shift to state yyact
special values              -> accept, error, or no action
```

So the huge `yy_action[]` table is the parser's precomputed decision table. Runtime parsing is mostly table lookup plus stack updates.

In `parse.out`, each state's action list is the readable version of part of that table:

```text
symbol -> action
```

Uppercase symbols are usually tokenizer tokens, like `SELECT` or `VALUES`. Lowercase symbols are non-terminals produced by reductions, like `select`, `oneselect`, or `values`.

If an action is not listed, the parser uses `{default}` if the state has one. If there is no listed action and no usable default, that table entry is an error/no-action.

A key nuance: the parser never re-matches old input. The parser stack keeps the current state up to date. Every shift pushes a new state; every reduce pops the matched RHS states and pushes the LHS state. That means the next token only needs:

```text
current top state + incoming token -> next action
```

To read a state in `parse.out`, look for the `*`:

```text
left of *  = already matched
right of * = still expected
```

A state is not the full history. It is a local summary. The parser stack of states preserves the larger context.

Practical reading heuristic:

```text
LHS ::= * RHS          possible thing to start next
LHS ::= prefix * rest  currently inside this rule; prefix already matched
LHS ::= RHS *          complete rule; ready to reduce
```

When `parse.out` prints a rule number in parentheses, that item is complete/reducible:

```text
(100) distinct ::= *        empty rule is complete
(180) expr ::= ID *         ID can reduce to expr
```

The action list still decides whether that reduce happens for the current lookahead. For example, `{default} reduce 100` means unmatched lookahead tokens reduce by rule `100`.

Example:

```text
trigger_cmd ::= scanpt insert_cmd INTO xfullname idlist_opt * select upsert scanpt
```

This is a context/progress item. It says this state was reached inside an INSERT-style trigger command, after matching the prefix up through `idlist_opt`; now it needs a `select`.

Items like:

```text
select ::= * WITH wqlist selectnowith
oneselect ::= * SELECT distinct selcollist from ...
values ::= * VALUES LP nexprlist RP
```

are expansion items. They describe possible ways to satisfy the needed `select`.

## State Flow For This Query

For:

```sql
SELECT name FROM users WHERE age = 30;
```

the main parser state flow is:

```text
state 0
  input SELECT
  shift SELECT -> state 329

state 329
  input ID(name)
  reduce distinct ::= empty -> state 227
  reduce sclp ::= empty -> state 422
  reduce scanpt ::= empty -> state 91
  shift ID(name) -> state 464

state 464
  input FROM
  reduce expr ::= ID
  shift expr -> state 22
  reduce scanpt ::= empty -> state 291
  reduce as ::= empty
  reduce selcollist ::= sclp scanpt expr scanpt as
  shift selcollist -> state 328
  shift FROM -> state 226

state 226
  input ID(users)
  reduce stl_prefix ::= empty -> state 235
  shift ID(users), pending reduce nm ::= ID

state 235 / pending reduce
  input WHERE
  reduce nm ::= ID
  shift nm -> state 389
  reduce dbnm ::= empty -> state 275
  reduce as ::= empty -> state 208
  reduce on_using ::= empty
  reduce seltablist ::= stl_prefix nm dbnm as on_using
  shift seltablist -> state 295
  reduce from ::= FROM seltablist
  shift from -> state 402
  shift WHERE -> state 113

state 113
  input ID(age)
  shift ID(age) -> state 464

state 464
  input EQ
  reduce expr ::= ID
  shift expr -> state 77
  shift EQ -> state 139

state 139
  input INTEGER(30)
  shift INTEGER, pending reduce term ::= INTEGER

pending reduce
  input SEMI
  reduce term ::= INTEGER
  shift term -> state 153
  reduce expr ::= expr EQ expr
  shift expr -> state 77
  reduce where_opt ::= WHERE expr
  shift where_opt -> state 401

state 401 onward
  reduce groupby_opt ::= empty -> state 400
  reduce having_opt ::= empty -> state 220
  reduce orderby_opt ::= empty -> state 399
  reduce limit_opt ::= empty
  reduce oneselect ::= SELECT distinct selcollist from where_opt groupby_opt having_opt orderby_opt limit_opt
  shift oneselect -> state 296
  reduce select ::= selectnowith
  reduce cmd ::= select
  reduce cmdx ::= cmd
  shift cmdx -> state 599
  shift SEMI, then finish
```

Very compressed shape:

```text
0
-> 329  after SELECT
-> 464  after name
-> 328/226 after select-list + FROM
-> 235/389/275/208/295/402 after users becomes FROM source
-> 113  after WHERE
-> 464  after age
-> 77/139 after age =
-> 153/77/401 after 30 becomes age = 30 becomes where_opt
-> 400/220/399 after empty GROUP/HAVING/ORDER/LIMIT
-> 296 -> cmd -> cmdx -> 599 -> done
```

The important build moments are:

```text
name       -> expr -> selcollist
users      -> nm -> seltablist -> from
age        -> expr
30         -> term -> expr
age = 30   -> expr via sqlite3PExpr()
WHERE expr -> where_opt
SELECT ... -> oneselect via sqlite3SelectNew()
```

## Building Expr Nodes

`sqlite3PExpr()` builds an `Expr*`, not a `Select*`.

For:

```sql
age = 30
```

the grammar rule in `parse.y` is:

```c
expr(A) ::= expr(A) EQ|NE(OP) expr(Y). {
  A = sqlite3PExpr(pParse,@OP,A,Y);
}
```

That creates an expression tree:

```text
      TK_EQ
      /   \
   age     30
```

In generated `parse.c`, the same rule appears inside `yy_reduce()` as a `case`, similar to:

```c
case 200: /* expr ::= expr EQ|NE expr */
{
  yymsp[-2].minor.yy454 =
    sqlite3PExpr(
      pParse,
      yymsp[-1].major,
      yymsp[-2].minor.yy454,
      yymsp[0].minor.yy454
    );
}
```

So the call path is:

```text
sqlite3Parser()
  -> yy_reduce()
       -> case for "expr ::= expr EQ expr"
            -> sqlite3PExpr()
```

## Building Select

`sqlite3SelectNew()` builds a `Select*`.

The relevant grammar rule is:

```c
oneselect(A) ::= SELECT distinct(D) selcollist(W) from(X) where_opt(Y)
                 groupby_opt(P) having_opt(Q)
                 orderby_opt(Z) limit_opt(L). {
  A = sqlite3SelectNew(pParse,W,X,Y,P,Q,Z,D,L);
}
```

For this query, it builds roughly:

```text
Select {
  pEList = [ Expr(ID "name") ]
  pSrc   = [ users ]
  pWhere = Expr(TK_EQ,
                left=Expr(ID "age"),
                right=Expr(INTEGER 30))
}
```

Important fields:

```text
pEList  = result expressions after SELECT
pSrc    = tables/sources after FROM
pWhere  = WHERE expression tree
```

`Parse *pParse` is not the AST. It is the compiler context: database handle, current VDBE, errors, registers, cursors, name resolution state, and other compile-time state.

## Select To Bytecode

The main function that works on `Select*` is:

```c
sqlite3Select(Parse *pParse, Select *p, SelectDest *pDest)
```

It reads:

```text
p->pEList
p->pSrc
p->pWhere
p->pOrderBy
p->pLimit
```

and emits VDBE instructions using helpers like:

```c
sqlite3VdbeAddOp0()
sqlite3VdbeAddOp1()
sqlite3VdbeAddOp2()
sqlite3VdbeAddOp3()
sqlite3VdbeAddOp4()
```

For the `FROM users WHERE age = 30` part, `sqlite3WhereBegin()` decides how to scan. Without an index, it emits a table scan.

For expressions like `age = 30`, expression codegen emits bytecode to read columns, compare values, and jump.

## VDBE Bytecode

Run:

```sql
EXPLAIN SELECT name FROM users WHERE age = 30;
```

Example output:

```text
addr  opcode       p1  p2  p3  p4        comment
0     Init         0   11                Start at 11
1     OpenRead     0   2                 open table users as cursor 0
3     Rewind       0   10                start scanning users
4     Column       0   1   1             r[1] = users.age
5     Ne           2   9   1             if r[1] != r[2] goto 9
7     Column       0   0   3             r[3] = users.name
8     ResultRow    3   1                 output r[3]
9     Next         0   4                 move to next row
10    Halt
11    Transaction
12    Integer      30  2                 r[2] = 30
13    Goto         0   1
```

Execution order is:

```text
0 -> 11 -> 12 -> 13 -> 1 -> 3 -> 4 -> 5 -> 7/9 -> 8 -> 9 -> ...
```

Meaning:

```text
r[2] = 30

open users as cursor 0

for each row in users:
  r[1] = row.age
  if r[1] != r[2]:
    skip output

  r[3] = row.name
  output r[3]
```

In C-like pseudocode:

```c
r[2] = 30;

open users as cursor0;

for each row in users {
  r[1] = row.age;

  if (r[1] != r[2]) {
    continue;
  }

  r[3] = row.name;
  emit_row(r[3]);
}
```

## Terms

`register`

A temporary VDBE storage slot. It is not a CPU register. It is a SQLite VM slot that can hold values like integer, text, null, blob, or real.

`cursor`

A VDBE handle for walking a table or index. In the bytecode above, cursor `0` is the scan over `users`.

`Init ... Start at 11`

The VM starts at instruction `0`, but `Init` jumps to setup code at address `11`. SQLite often places setup code after the main body, then jumps back.

`ResultRow`

Return a row to the caller. For `ResultRow 3 1`, SQLite outputs one column starting at register `3`.

`Ne`

Not-equal comparison. `Ne 2 9 1` means compare register `1` with register `2`; if they are not equal, jump to address `9`.
